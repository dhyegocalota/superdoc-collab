# 0020. Invite-only accounts with a first-claim admin

- Status: Accepted
- Date: 2026-10-17
- Deciders: Dhyego Calota (owner); Claude (advisor)
- Inspired by: [0005](0005-authentication-with-better-auth.md) (open sign-up, seeded demo users), [0010](0010-documents-ownership-and-share-links.md) (token hashing for share links), [0011](0011-process-wide-llm-cost-caps.md) (the budget an open sign-up exposes), the first Railway deploy (an instance anyone can join spends the owner's model key)

## Context

The brief put real authentication out of scope, so ADR 0005 chose open sign-up and four seeded demo users. The app now runs on a public URL with the owner's OpenRouter key behind it, and it is meant to be installable by other people. Open sign-up means anyone who finds the URL can create an account, upload documents and consume the process-wide LLM budget; the shared demo password is a production credential. There is no administrator and no way to decide who joins. The app sends no e-mail, so invitations must be links carried by hand.

## Decision

- **First claim.** A fresh instance has no users and is *unclaimed*. The first account created claims it and gets `role = admin`. From then on, sign-up requires a valid invite. The claim is the last step of every install path and is stated as such in the README, the runbook and the agent prompt, because the window between deploy and claim is open to whoever finds the URL.
- **Roles** come from Better Auth's `admin` plugin (`admin`, `user`); the gate is a local plugin with `matcher`-based `before` and `after` hooks on `/sign-up/email`; the `after` hook makes the earliest user admin or consumes the invite, and deletes the fresh user otherwise. The plugin's own `/api/auth/admin/*` endpoints are answered 404 at the Hono layer, because they would let an admin impersonate users, create accounts outside the gate and bypass the last-admin rule. No second account-creation path exists.
- **Invites** are single-use links generated by an admin, valid for seven days, stored as a sha256 hash with the share-link helper; state is derived from timestamps, never stored. An admin can revoke pending invites and promote or demote admins; the last admin can never be demoted, by anyone, so an admin steps down only when another admin exists (owner ruling 2026-10-17).
- **No seed in production.** The demo users exist only for E2E and agentic tests, as plain users next to a test-only admin.

## Alternatives considered

| Option | Pros | Cons | Why not |
|--------|------|------|---------|
| Admin from `ADMIN_EMAIL` and `ADMIN_PASSWORD` at boot | no claim window; pure env install | a password in the environment of every host; rotation means redeploy | the owner preferred the claim and an install flow that ends with it |
| Admin created by a CLI command | explicit | needs a shell on the container after deploy | one more manual step on managed hosts |
| Keep sign-up open, cap per user | nothing to build | caps do not stop account creation; the key still pays for strangers | does not answer "who may join" |
| Admin sets the invitee's password | simplest invite | the password travels in clear and there is no password change | weaker than a link that dies on use |
| Reusable invite link | one link for a team | leaks for as long as it is valid | the owner chose single use |
| Disable sign-up and create accounts through an own endpoint | explicit flow | duplicates account creation outside Better Auth; a second form | the hook keeps one path |

## Consequences

- `GET /api/setup` discloses whether the instance is claimed, and nothing else.
- Two concurrent first sign-ups produce exactly one admin (earliest row).
- An instance can end up claimed without an admin only if the after hook fails; `pnpm admin:promote <email>` recovers it.
- ADR 0005's "open sign-up" and "demo users seeded for the demo" bullets no longer hold in production; 0005 stays for the stack choice and the socket handshake.

## Evidence

- `docs/features/invite-only-access/test-plan.md` after the build; the unit suites named in the spec's test strategy.

## Revisit when

- E-mail delivery arrives: invites could be sent, and the claim could become an e-mailed setup link.
- Organisations arrive: admin becomes per-organisation and invites carry a target organisation.
