# SuperDoc v2 collaboration

Citations to `poc/...` name files of the proof of concept removed on 2026-10-17; the facts stand, the evidence is summarized in ADR 0001–0004.

SuperDoc facts about the browser UI (editing surface, focus, zoom, iframes) live in `.claude/rules/web-ui.md`.

## Versions
- `superdoc` 2.23.0, `@superdoc/sdk` 2.20.0, `@hocuspocus/server` 2.15.3, `@hocuspocus/provider` ^2.15.3, `yjs` ^13.6.33. (poc/package.json)

## Client configuration
- A document is collaborative through `v2Collaboration: { providerType: 'hocuspocus', documentId, serverUrl, roomMode: 'create' | 'join', token }`. (poc/client/main.ts)
- The server opens the room with `roomMode: 'create'` and the stored DOCX (the SDK on the bootstrap path); every browser uses `'join'`, except the owner's browser for a document the memory guard refused (a device job), which uses `'create'` ([ADR 0049](../../docs/adr/0049-the-uploader-previews-locally-and-a-refused-file-is-prepared-on-the-device.md)). (apps/server/src/history/projection-worker.ts, ADR 0048)
- The room name on the server is `sd2/v2.1/<documentId>`. (poc/tests/harness.ts, ADR 0001)
- Readiness is signalled by `onCollaborationReady`; connection changes by `onCollaborationConnectionChange`. (poc/client/main.ts)
- Text is read with `superdoc.activeEditor.doc.getText({})`. (poc/client/main.ts)

## SuperDoc limits
- v2 gives no ProseMirror access and no version-history API. (ADR 0001)
- The `diff.capture/compare/apply` payload is opaque. (ADR 0001)
- `trackChanges.list()` returns author, ISO date, inserted/deleted text, `imported: true` and the room's `blockId` scheme; it works in the browser and in Node via `@superdoc/sdk`. (poc/RESULTS.md, poc/tests/node/t10-imported-tracked-changes.test.ts)
- `comments.list()` returns `creatorName`, `createdTime` (epoch milliseconds), `text`, `parentCommentId` for a reply (no `target`), `trackedChange: true` for a tracked-change card, and `target.segments[].blockId` in the same scheme as `trackChanges.list()`. (libs/history/src/imported-comments.ts, docs/features/import-comments/spec.md)
- The room `Y.Doc` is an operation journal. Top-level maps: `meta`, `package`, `operations`, `checkpoints`, `shards`, `content`, `root-op-evidence`. Transactions carry `createdByClient` and `createdAtMs`; `author` is always `headless-kernel`, so identity comes from the transport. (poc/RESULTS.md)
- The room grows about 2.8 KB per keystroke by itself. (poc/RESULTS.md)

## Editing behavior
- A keyboard paragraph merge (Backspace at a paragraph start, Delete at an end) is a no-op in collaborative mode; use `doc.blocks.merge({ first, second })`. (poc/RESULTS.md, poc/tests/e-edge-cases.spec.ts)
- Undo is recorded as a deletion by the undoer; it emits reversed per-character deletions. (poc/RESULTS.md E8; reversed per-character form from the task brief)
- Under concurrent remote edits, a click on a text run occasionally leaves focus on `BODY`; the caret occasionally lands out of order under fast concurrent typing. Neither affects convergence. (poc/RESULTS.md)

## Build
- The client must be built and served with `vite preview`; the dev server fails with SuperDoc's worker (task brief). The POC pins port 5199. (poc/vite.config.ts)

## Hocuspocus server
- Use `new Hocuspocus({...})`; the exported `Server` is a singleton. (poc/RESULTS.md, poc/server/collaboration-server.ts)
- `onAwarenessUpdate` receives the document creator's context, not the sender's; tie awareness clientIds to sockets through `document.connections[*].clients`. (poc/RESULTS.md, ADR 0002)
- `onAuthenticate` returns `{ userId }` as the connection context. (poc/server/collaboration-server.ts)
- In `apps/server` it returns `{ userId, documentId, actor, bootstrapAttempt, tabId, impersonationEndsAt }`. The upgrade path in `request.url` picks the credential: `/collaboration` takes the session cookie only, `/collaboration/agent` takes a room token in the `token` field only and skips the `Origin` check, `/collaboration/bootstrap` takes a bootstrap token only and skips it too. Both token paths are loopback-only. (apps/server/src/collaboration/collaboration-server.ts, ADR 0025, ADR 0048)
- The room token and the read-only flag are fixed when an SDK session opens; replace a cached session when the role, the name or the token age changed. (apps/server/src/agent/agent-sessions.ts, docs/learnings/2026-10-17-a-reused-sdk-session-keeps-the-room-token-and-read-only-flag-from-open.md)
- Load the room with `Y.applyUpdate(document, state, 'update-log-replay')`; `onChange` skips that origin. (poc/server/collaboration-server.ts)
- `onCollaborationConnectionChange` reported `synced -> degraded -> degraded` across a server restart and never a recovery state, though sync resumed; do not rely on it for recovery. (poc/RESULTS.md)
- The server bootstraps every new document: right after the upload (and a blank create) `RoomBootstrap` queues one job in the light lane (a `word/document.xml` of up to `BOOTSTRAP_LIGHT_MAX_BYTES` inflated bytes) or the heavy lane, one at a time per lane with owners served in turns, and the projection worker opens the stored DOCX through the `SuperDocClient` of that lane (its own host process, `requestTimeoutMs` raised to `BOOTSTRAP_HOST_TIMEOUT_MS`, secrets removed from its environment, heap capped like the worker, disposed after every bootstrap) with `roomMode: 'create'` on `/collaboration/bootstrap`. A browser never creates a room; every opener gets `RoomMode.Join` and the open answer carries `bootstrap` (stage Queued, Preparing, Ready or Failed; `total` is the inflated `word/document.xml` size (`documentXmlBytes`) times `BOOTSTRAP_STATE_BYTES_RATIO`, `done` the bytes of state received from the SDK host so far, `stateBytes` known at Ready). A blank create never waits for a conversion: the first blank of a process converts in the light lane and keeps its committed state, and every later blank is committed from that state at once through `RoomBootstrap.requestBlank`. The SDK reports nothing during the conversion. An uncommitted document nobody bootstrapped is bootstrapped by its first open; a Failed one is started again by the first open after `BOOTSTRAP_RETRY_COOLDOWN_MS`, and a run interrupted by a worker death is run once more on a new attempt. `POST /api/documents` answers 429 when the user spent `UPLOADS_PER_MINUTE` or has a bootstrap waiting in the lane of the new file, 413 when the container memory cannot hold the document (`MEMORY_LIMIT_MEGABYTES`), and 415 for a `word/document.xml` inflating past `MAX_DOCUMENT_XML_BYTES`. (apps/server/src/collaboration/room-bootstrap.ts, apps/server/src/history/projection-worker.ts, ADR 0048)
- The bootstrap path takes a room token with actor Human and an attempt (`signBootstrapToken`), authenticates as the document owner with actor Human, is loopback-only without an `Origin` check, and spends no open budget. The write fence is the attempt: a bootstrap socket writes only while `RoomBootstrap.isCurrent` says its attempt is the registry's, the attempt ends when the run has ended with the commit in, and `authenticateBootstrap` refuses a committed room, so a host that outlives a failed job, a restart or its own run is refused and its writes dropped; a member, reader or agent on an uncommitted room is refused. The scheduler holds a bootstrap posted during a worker recycle until the fresh worker exists. (apps/server/src/collaboration/authenticate-bootstrap.ts, apps/server/src/collaboration/collaboration-server.ts, ADR 0048)
- A document the server cannot hold (`isPreparableByServer` false: the stored file does not fit `MEMORY_LIMIT_MEGABYTES`) or that the owner's device asked to prepare (`preparation=device` on a heavy file, `RoomBootstrap.requestOnDevice`; a light file ignores the flag; the heap refusal, the heavy room admission, the per-user cap and the hourly heavy budget still apply; the job estimates with `DEVICE_MS_PER_MEGABYTE`) is never queued: `RoomBootstrap.request` registers a device job in Preparing, and the owner's open answer is `RoomMode.Create` while it is not Ready. The owner's member socket claims the job's attempt in `onAuthenticate` (`claimDevice`: one live claim per job, shared by the sockets of the claiming tab, a second tab is refused and answered Join; the socket passes `heavyRooms.admitsDevice` and releases its place on disconnect), writes under the same `isCurrent` fence, commits through `bootstrap.commit`, and keeps writing as the committing attempt; a claimed socket whose attempt is not current is read-only, a claimed socket that closes before the commit fails the job (`deviceClosed`), a job not committed within `DEVICE_JOB_LIFETIME_MS` fails, and a Failed job is registered again by the owner's reopen at once when its claiming tab closed and the collaboration server no longer holds its room (`reopenDevice`; while the room is held the open answers Preparing so the tab retries), otherwise by a reopen after the retry cooldown; the open answer keeps `preparedOnDeviceOf` while a device job is Preparing or Failed. Everyone else joins and reads `preparedOnDeviceOf`. (apps/server/src/collaboration/room-bootstrap.ts, apps/server/src/collaboration/collaboration-server.ts, ADR 0049)
- `onChange` fences first: a refused update is dropped and logged once per connection with the document id, never the payload. The first update of the current attempt whose live room satisfies `isBootstrapCommitted` goes through `bootstrap.commit` (append and snapshot of the live room in one transaction, then `RoomBootstrap.ready` with the state size); every other update is appended. `onLoadDocument` restores nothing while the room is uncommitted, so a new attempt starts empty and abandoned partials stay in the log only. (apps/server/src/collaboration/collaboration-server.ts, ADR 0033, ADR 0048)
- Before the editor is ready only a `failed` connection report or a connection exception ends the load with the editor failure notice (`EDITOR_FAILED_MESSAGE`); `lost` and `reconnecting` are ignored and nothing reaches the banner. After ready, reports and exceptions reach the banner with their reason. (apps/web/src/features/editor/superdoc-editor.tsx)
- `DELETE /api/documents/:documentId/members/:userId` (owner only) deletes the member row first and then closes that user's connections in every room of the document with 4404 and `ACCESS_REVOKED_REASON`, so a reconnect fails `onAuthenticate`; it also closes that user's sockets in the version rooms (`VersionRooms.closeUser`), and the `connected` hook re-checks the role and closes a socket admitted just before the removal with the same code; removing the owner answers 400 and an unknown member 404. (apps/server/src/documents/documents-routes.ts, apps/server/src/collaboration/collaboration-runtime.ts, apps/server/src/collaboration/version-rooms.ts, apps/server/src/collaboration/collaboration-server.ts, docs/features/revoke-access/spec.md)
- Close codes: 4401 for a stale bootstrap attempt, 1008 for a rate breach, 1009 for a frame over `MAX_SOCKET_MESSAGE_BYTES`. `ws` closes with 1009 on its own, and `terminateOnError` returns early on a CLOSING socket so that close frame reaches the client. (apps/server/src/collaboration/attach-collaboration.ts, ADR 0034)
- The rate limit lives at the `ws` layer, not in a Hocuspocus hook, because `connection.close()` inside `beforeHandleMessage` does not stop the message. `SocketMessageLimit` counts every frame per socket from the first one, before authentication, in a rolling second. The counter keeps two windows per socket (`FrameBucket`): `MAX_SOCKET_UPDATE_FRAMES_PER_SECOND` (1000, everything but awareness) and `MAX_SOCKET_AWARENESS_FRAMES_PER_SECOND` (5000), because SuperDoc sends about six update frames per keystroke and the provider flushes about three awareness frames per keystroke in one burst at the next pause (ADR 0040). A wrapper around the socket's event dispatch (`withholdOverclaims`, on version-room sockets too) reads an awareness frame only as far as its entry count (`awarenessEntryCountOf`, which looks at most six bytes deep per varint and treats a longer or still-continuing one as an unbounded count) and closes a socket whose frame claims more than `MAX_AWARENESS_ENTRIES_PER_FRAME` (64) entries with 1008 and `SOCKET_AWARENESS_ENTRIES_REASON` before Hocuspocus decodes anything, because one frame can claim a million ids and Hocuspocus stores, adds and broadcasts every one of them; the stock provider relays every awareness change it applies, other peers' ids included, one entry per changed peer, which is why the cap is 64 and not the eight ids a connection may hold. `onAwarenessUpdate` closes a connection that holds more than `MAX_AWARENESS_CLIENT_IDS_PER_CONNECTION` (8) ids over several frames, and `trackAwarenessOwners` adopts an id no connection holds into the sender (Hocuspocus files a replayed or reconnected id under `updated`, so it never joins `connection.clients` by itself) and binds every id the sender adds or takes over to its user (an id held by another socket of the same user moves to the sender, because a reconnect overlaps the old half-open socket; nothing closes on the origin of an id, only structural breaches close); a relay at the clock the room already holds is filed as no change and spared. The wrapper reads only the count and header varints; the hook walks the entries once and closes a malformed one with the entries reason. `beforeHandleMessage` drops (empties the frame in place and logs one warn line per socket per minute; the socket stays open, because document sync shares it) a frame with an entry for an awareness client id bound to another user (the user whose connection first announced it, kept across socket closes, seeded from every recorded client identity (observed and declared) when the room loads and forgotten when it unloads) at a clock above the one the room holds; a relay at the held clock passes (the room ignores a non-null one and applies a removal), and a user's own ids pass at any clock. Throwing from that hook stops the message but closes the socket; `connection.close()` inside it does not stop the message. The frame past the rate cap still reaches the room handler (the emitter runs every listener of that event), then the listeners are removed so nothing after it does, and the socket closes with 1008; an overclaiming frame is withheld from every listener and later messages on the closing socket are dropped. Logs carry no payload. (apps/server/src/collaboration/socket-message-limit.ts, ADR 0034, ADR 0040)
- The browser upgrade is refused before `handleUpgrade` unless the request carries a session the auth layer reads, so an unauthenticated client cannot queue frames. The agent path cannot be checked there because its room token travels in the first protocol message; it is loopback-only. `onConnect` pins a socket to the first document name it names and closes any other name with 1008 and `SOCKET_SINGLE_DOCUMENT_REASON`, because Hocuspocus queues frames for a document that never authenticates. (apps/server/src/collaboration/attach-collaboration.ts, apps/server/src/collaboration/collaboration-server.ts, ADR 0034)
- Commit detection is snapshot-first: an abandoned partial and the winner's seed are concurrent Yjs writes, so replaying the whole log can end as "never committed". `isCommitted` and the projection start read the commit snapshot, and fall back to the log scan only when no snapshot exists. (apps/server/src/collaboration/bootstrap-state.ts, libs/history/src/projection.ts, ADR 0033)
- The commit snapshot is `Y.encodeStateAsUpdate` of the live room, never a `materialize` of the log, and it is written in the same SQLite transaction as the committing update (`UpdateLog.appendCommitted`). (apps/server/src/collaboration/bootstrap-state.ts, ADR 0033)
- The fence trusts the server's commit answer as well as the live room marker, because any member can overwrite `meta.bootstrapState` in the live room. `bootstrap.isCommitted` keeps the scan progress of an uncommitted room (rows read plus the partial `Y.Doc`) and resumes after it, so repeated opens and authentications never replay the log from zero. (apps/server/src/collaboration/collaboration-server.ts, apps/server/src/collaboration/bootstrap-state.ts, ADR 0033)
- Every server-initiated close is bounded by one setting: the socket server is created with `closeTimeout: SOCKET_CLOSE_GRACE_MS`, so a peer that ignores any close frame (1008 breach, one-document, idle, 4403, 1009) loses the socket after one second instead of ws's 30. `@types/ws` does not declare the option, so the options constant adds it by type. (apps/server/src/collaboration/attach-collaboration.ts, ADR 0034)
- The commit-scan progress of uncommitted documents lives in an `LruMap` of `BOOTSTRAP_SCAN_CACHE_ENTRIES`; an evicted document rescans from sequence 0. (apps/server/src/collaboration/bootstrap-state.ts, ADR 0033)
- A browser whose session expired is let through the upgrade and closed with 4401 and the reason `Session expired`, so the provider treats it as an authentication failure and stops retrying; Hocuspocus never sees the socket. A request with no cookie, or one whose session lookup throws, is destroyed, so the provider retries. (apps/server/src/collaboration/attach-collaboration.ts, ADR 0034)
- The fence branches on the attempt first: a socket with an attempt is checked by `isCurrent` alone, so a bootstrap update never queries the log or the snapshots; only an attempt-less socket consults the live marker and `bootstrap.isCommitted`. (apps/server/src/collaboration/collaboration-server.ts, ADR 0048)
- A user may open at most `OPEN_UNCOMMITTED_PER_MINUTE` (never above `BOOTSTRAP_SCAN_CACHE_ENTRIES`) distinct documents that are not yet known committed per rolling minute; a document counts once per user and minute (`OpenBudget`), so waiting-page polls and reconnects are free. `runtime.roomModeFor` answers Join from the registry while the bootstrap of the document is queued or preparing, and otherwise consults the budget before any log scan and is the only way the open route, `onAuthenticate`, the agent room locator and the export tool decide a room mode: 429 with `Retry-After`, access denied, or an agent tool error. A room the process knows is committed (cache or projection cursor) is never limited. So one user cannot thrash the bounded scan cache on any path. (apps/server/src/collaboration/room-modes.ts, apps/server/src/limits/open-budget.ts, ADR 0033)
- `onException` payloads are narrowed by `exceptionOutcome` in `apps/web/src/features/editor/superdoc-exceptions.ts`: a diagnostic with `severity: 'warn'` is logged, `edit-rejected` is recoverable, a `collaborationReason` or the `worker-transport-failed` code is a connection failure, everything else including error diagnostics is fatal. Never treat every exception as fatal: SuperDoc raises warn diagnostics for conditions the editor survives. (ADR 0032)
- `useConnectionState` merges the transport reading from `onCollaborationConnectionChange` (`transportReportOf`) with the members flag: Lost, Reconnecting and Failed come from the callback alone, Failed is sticky until Reload, and Recovered needs a members answer that finished after the outage began (`membersAnsweredAt` later than the recorded loss time) with the flag true. Recovered shows for `RECOVERED_NOTICE_MS`, then Online; a `synced` or `recovered` callback only refetches members. (apps/web/src/features/editor/use-connection-state.ts, ADR 0032)
- Reload in the Failed banner awaits a refetch of the open query and the document's file query, resets the connection, then bumps `editorGeneration`, the `key` of `SuperDocEditor` and an input of `useEditorSetup`, so the editor remounts with the refetched room mode. The old instance's handlers stop at an `isActive` flag. Edits that had not synced are lost, and the banner says so. (apps/web/src/features/editor/document-page.tsx, apps/web/src/features/editor/superdoc-editor.tsx)
- The members answer carries `isCurrentUserOnline`, whether the server holds a live Hocuspocus connection for the caller in that room; `useMembers` returns it as `null` before the first answer and after a failed poll, never as a stale `true`. The flag is per tab: the socket URL and the members request both carry the page load's `tab` query, the connection context stores it, and the route answers from `runtime.onlineTabIds`; a request without `tab`, or with one that is not a UUID (`isTabId`), keeps the per-user answer, and `onlineTabIds` counts only the asking user's connections, so one member cannot keep another's tab online. (apps/server/src/documents/documents-routes.ts, apps/server/src/collaboration/collaboration-runtime.ts, apps/web/src/features/editor/use-members.ts, ADR 0032)
- better-auth sends no email here: `sendResetPassword` stores the token in `PasswordResetLinkCapture` keyed by a per-request nonce (the `redirectTo` echoed in the callback URL), the admin route awaits `auth.api.requestPasswordReset` and `take`s it, and `take` clears the slot and throws `PasswordResetLinkNotCapturedError` when it is empty. The public `/request-password-reset` path is in `DISABLED_PATHS`; `/reset-password` stays public because the token is the credential, and `revokeSessionsOnPasswordReset` ends every session of the user, and `onPasswordReset` also closes the user's sockets in every room and deletes their OAuth grants. (apps/server/src/admin/password-reset-links.ts, apps/server/src/auth/auth.ts, docs/features/password-reset-link/spec.md)
- Archiving is better-auth's `banUser` called from `POST /api/admin/users/:id/archive` through `UserAccess` (the plugin's own `/api/auth/admin/*` paths stay 404): the ban deletes the user's sessions, then `revokeOAuthGrantsOf` and `closeConnectionsOfUser` end their grants and sockets; `bannedUserMessage` is `ACCOUNT_ARCHIVED_MESSAGE`, so a sign-in answers 403 with it, and a share-link accept by an archived user answers the same message with no grant. The last active admin answers 409 and archiving yourself 400. Impersonation is `impersonateUser` from `POST .../impersonate` (one hour, `IMPERSONATION_SESSION_MS`; archived users, admins and yourself are refused with 400): the route forwards the plugin's `Set-Cookie`, logs one line of ids, and `/api/me` carries `impersonatedBy`. `/api/auth/admin/stop-impersonating` is the one plugin admin path let through, and it answers 415 unless the request carries a JSON content type. (apps/server/src/admin/user-access.ts, apps/server/src/admin/user-access-routes.ts, apps/server/src/http/app.ts, ADR 0046, docs/features/admin-archive-and-impersonate/spec.md)
- The socket server negotiates permessage-deflate (threshold 1 KiB, level 1, no context takeover either way, a 12-bit window and memory level 3 which cost about 79 KiB resident per socket that sent one frame against 336 KiB at the `ws` defaults, four concurrent compressions); `ws` applies `maxPayload` to the inflated size, so the caps of ADR 0034 and ADR 0040 hold on what the room receives, and `SocketMessageLimit.exceedsInflatedBudget` closes with 1008 a socket that inflates more than `MAX_INFLATED_BYTES_PER_SECOND` (80 MiB) in a rolling second, and a socket the server has not yet sent its Authenticated reply may inflate only `PRE_AUTHENTICATION_MAX_INFLATED_BYTES` (64 KiB) in total because Hocuspocus queues pre-authentication frames without a bound, only that reply lifts the cap (`auth-reply.ts` reads the outgoing frame), and a permission-denied reply closes the socket with 1008 because Hocuspocus 2.15.3 neither closes it nor drops its queue; both caps skip the loopback bootstrap socket. The large fixture's 36.6 MB sync is about 5 MB on the wire. The snapshot stays Yjs V1: V2 is 29 percent smaller but decodes 28 percent slower and the wire is V1 anyway. (apps/server/src/collaboration/attach-collaboration.ts, docs/features/snapshot-compression/spec.md)
- Backpressure on heavy documents: `RoomBootstrap.predictedWaitMs` is what is left of the running job of a lane plus every queued job, each at its `documentXmlBytes` times the measured rate, and `POST /api/documents` answers 503 with `Retry-After` and `bootstrapBusyMessage` for a heavy file when it is above `MAX_BOOTSTRAP_WAIT_MS` (environment override of the same name). A Queued open answer carries `queuePosition` (documents ahead, the running one included, in the owners' turn order) and `queueWaitMs`; both are null in every other stage. (apps/server/src/collaboration/room-bootstrap.ts, docs/features/backpressure)
- `createRoomMemoryRelease` budgets the heap of every loaded room by its state bytes times `HEAVY_ROOM_HEAP_BYTES_PER_STATE_BYTE`, lets heavy rooms (above `LARGE_ROOM_STATE_BYTES`) use `1 - SMALL_ROOMS_HEAP_SHARE` of `roomHeapBudgetMegabytes` (the smaller of the container and the server heap formulas, `SERVER_HEAP_MEGABYTES` from the entrypoint, override `ROOM_HEAP_BUDGET_MEGABYTES`) and measures rooms that received updates again only when an admission is short. `createHeavyRoomAdmission` checks the open route with `fits` (no reservation, 503 with `HEAVY_ROOMS_FULL_MESSAGE`), reserves at the socket through `admits` (denied with `HEAVY_ROOMS_FULL_REASON`, closed with `HEAVY_ROOMS_FULL_CLOSE_CODE`) and reserves at upload through `reserveForUpload` (one per owner, released when the registry ends the job, `RoomBootstrap`'s `onEnded`); rooms are measured again at most once per `ROOM_REMEASURE_COOLDOWN_MS`; a heavy upload without headroom is refused (503), one owner is limited to `MAX_HEAVY_CONVERSIONS_PER_HOUR` heavy uploads (429), one user holds at most `MAX_HEAVY_ROOMS_PER_USER` heavy rooms (refused with its own sentence, reason and close code 4504), a Failed document is retried by an open at most `BOOTSTRAP_MAX_RETRIES` times and each heavy retry spends the hourly heavy budget, and the bootstrap socket is never asked. Idle rooms are never closed to make room: a server-initiated close makes the provider reconnect at once. (apps/server/src/collaboration/heavy-room-admission.ts, apps/server/src/collaboration/room-memory-release.ts)
