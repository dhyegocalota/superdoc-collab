## Adversarial review

The reviewer picks the three claims most likely to be wrong and tries to refute each.

- [x] Claim 1: a dead invite can never create a user, even under concurrency — attack: two parallel sign-ups with one token; a revoke racing a sign-up; `accept` forced to return false; result: <refuted | held> — attack (reviewer, 2026-10-17): twenty rounds of three concurrent sign-ups on one token, a revoke landing between the before and after hooks in twenty rounds, and `accept()` with its pending condition removed; result: held (one user per round, revoke gave 403 and no user, the mutation turned `invites.test.ts` red).
- [x] Claim 2: no request creates an account or changes a role outside the gate and the admin routes, admin or not — attack: every `/api/auth/admin/*` path with the admin cookie, including case, encoding and dot-segment variants; `role` in the sign-up body and in `/update-user`; result: <refuted | held> — attack (reviewer): 23 raw path variants and one absolute-form target with the admin cookie (double slash, case, %61, %2561, %2F, dot segments, trailing slash, `;`, backslash, `/api/auth/api/auth/`); `role` in the sign-up body; `banned` on `/update-user`; result: held (all 404, role unchanged, 400 `FIELD_NOT_ALLOWED`).
- [x] Claim 3: the instance never ends up with zero or two admins — attack: two concurrent first sign-ups, twenty rounds; two admins demoting each other concurrently; the last admin demoting themselves; result: <refuted | held> — attack (reviewer): twenty rounds of three concurrent first sign-ups; twenty rounds of two admins demoting each other or themselves; the last admin demoting themselves; migration `0004` on a populated database; result: held under attack, refuted by the upgrade (zero admins after migrating a database with accounts). Fixed in the Railway runbook's upgrade path (`admin-promote` or reset and claim), `3bd9c52`.

## Coverage honesty

- Two screenshots (`03-admin-invite-dialog.png`, `07-copy-failed.png`) show about ten characters of invite tokens from the local walk stack, which was destroyed with its volume after the walk; those tokens no longer resolve anywhere. Not redacted.
- The invite lookup has no rate limit of its own (Better Auth's limiter covers `/api/auth/*` only); tokens are 256-bit, so this costs at most one indexed lookup per request.

- The walk ran on `a4c7edf`, before the review fixes in `3bd9c52`. The three behaviours those fixes added are pinned by tests, not walked: the 400 for an unknown or oversized zone on `/update-user` (`auth-admin-endpoints.test.ts`, real HTTP), the error shown when `/api/setup` fails (`sign-up-page.test.tsx`), and the setup refresh after a successful submit (`use-auth-submit.test.tsx`).

- A network cut after the create request reaches the server but before its answer reaches the page leaves a pending invite whose link was never shown. It admits nobody (the token exists only in that lost response), is visible as Pending, can be revoked, and expires in seven days. Accepted rather than fixed.

- The claim flow is not in the Playwright suite (the shared stack is seeded and therefore claimed); it is pinned by real-HTTP server tests and by the MCP walk on a fresh stack.
- The plugin's own endpoints are covered by a 404 per listed path plus the reviewer's variant probe, not by an exhaustive list of every plugin route.
- The 403 that follows a deleted post-gate user still carries a `Set-Cookie` for a session that no longer exists; the cookie is dead because the session row cascades. Not tested beyond the user count.
- Browser-zone rendering of invite times is asserted against `formatTimestamp`'s output, not a literal; zone correctness itself is the `timezone-preference` feature.
